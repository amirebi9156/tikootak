# تحلیل کامل وضعیت: Songbird در برابر TIKOOTAK (۲۶ اکتبر ۲۰۲۶)

> روش: سورس Songbird 0.13.1 (MIT) را کلون و خواندم (مستندات، ۴۱ migration، `server/api`، `server/lib`، `appSettings.js`، `client/src`، پنل ادمین). وضعیت TIKOOTAK را از سورس خودمان (gateway، web-src، Caddyfile، admin.html) بررسی کردم.
> علامت‌ها: ✔ هست | ✘ نیست | ◐ ناقص. جاهایی که فقط با جستجوی کد (grep) نبودن چیزی را نتیجه گرفتم با «(grep)» مشخص شده؛ DeepSeek باید قبل از ساخت دوباره تأیید کند.

## ۱) دو پروژه چه فرقی دارند
| | Songbird | TIKOOTAK |
|---|---|---|
| ماهیت | چت ساده و سبک (DM، گروه، کانال، تماس ۱‌به‌۱) | پلتفرم اجتماعی: چت + تماس گروهی + ریلز + استوری + موزیک + پروفایل |
| هستهٔ چت | کد خودشان (Node/Express + SSE/WebSocket) | **Matrix/Synapse** (استاندارد، E2EE واقعی) |
| تماس | WebRTC همتابه‌همتا ۱‌به‌۱، TURN اختیاری | **LiveKit** (گروهی) + TURN داخلی |
| رمزنگاری پیام | **در حالت سکون سمت سرور** (کلید در `.env`؛ خود سرور می‌تواند بخواند) | **سرتاسری (E2EE)**؛ سرور محتوا را نمی‌بیند |
| فرانت | React 19 + Tailwind 4 | React 18 + CSS دست‌ساز، RTL/فارسی‌محور |
| نصب | منوی `songbird-deploy` (Ubuntu، nginx + systemd + Node) | `bootstrap.sh` + Docker Compose؛ از UI33 منوی `tikootak` |
| جابه‌جایی سرور | بکاپ/ریستور DB | بکاپ رمزشده + `migrate.sh` (کامل‌تر) |

نتیجه: «چت» ما از نظر ویژگی قوی‌تر است؛ Songbird در **عملیات و پنل مدیریت** جلوتر است.

## ۲) دیتابیس
| | Songbird | TIKOOTAK |
|---|---|---|
| موتور | SQLite (better-sqlite3، در حافظه با persist) **یا** PostgreSQL؛ لایهٔ `knex`؛ Redis اختیاری (صف BullMQ، نشست، pub/sub) | Postgres فقط برای Synapse؛ gateway: SQLite فایلی با WAL (~۲۰ جدول) |
| migration | **۴۱ migration نسخه‌دار** + جدول `meta`؛ ارتقا امن | ✘ ندارد؛ `CREATE IF NOT EXISTS` + `ALTER` داخل `try/catch` پراکنده (feed، music، profiles، index…) |
| کلید اصلی | UUID (migration 036) | رشتهٔ Matrix (`@u:domain`) و ID های متنی |
| تنظیمات runtime | جدول `app_settings` + رجیستری `SETTING_DEFS` (نوع، حداقل/حداکثر، گروه، secret، نیاز به ری‌استارت)؛ اولویت **env > DB > پیش‌فرض** | جدول `settings` ساده (فقط ثبت‌نام و سقف‌ها) |
| لاگ ممیزی | جدول `admin_audit_logs` + کاتالوگ ~۳۰ رویداد | `audit_log` (✔) ولی بدون کاتالوگ و فیلتر |
| نشست | جدول `sessions` + کوکی `sid` (HttpOnly، SameSite=Lax، ۱۴ روز) | توکن Matrix (Bearer)؛ نشست‌ها را خود Synapse نگه می‌دارد |
| ایندکس/کارایی | ایندکس‌های اختصاصی برای آمار ادمین، چت، خواندن پیام | ایندکس‌های پایه |

**توصیه:** SQLite برای gateway تا چند هزار کاربر کافی است؛ نیازی به Postgres/Redis نیست. اما **migration نسخه‌دار الزامی است** (ستون ۱ اولویت)، چون `tikootak update` وقتی بدون سیستم migration باشد روی داده‌ی قدیمی ریسک دارد.

| پروکسی خروجی | `PUSH_PROXY_URL`، `STORAGE_PROXY_URL`، … (برای شبکهٔ فیلتر) | — | مفید برای ایران |

## ۵) پنل ادمین: مقایسهٔ دقیق
Songbird: داشبورد، کاربران، چت‌ها، سرویس‌ها، تنظیمات، لاگ‌ها، اکشن‌ها (۷ تب). TIKOOTAK: نمای کلی، کاربران، محتوا، گزارش‌ها، درخت دعوت، تنظیمات، ممیزی (۷ تب).

|---|---|---|---|
| داشبورد | کاربران/آنلاین/جدید ۷ روز/بن، چت/گروه/کانال، پیام کل و ۲۴ساعته، فایل، دستگاه‌های push، نشست فعال، حجم DB، RSS، uptime + **CPU/RAM سیستم/دیسک زنده** | کاربران، حجم هر کاربر، سقف‌ها | **اضافه شود:** متریک سیستم، پیام ۲۴ ساعته، آنلاین |
| کاربران | صفحه‌بندی/مرتب‌سازی/فیلتر سمت سرور، ساخت کاربر، ویرایش (نام، آواتار)، **ریست رمز**، نقش، ban/unban، حذف | لیست، جزئیات، ban کامل، purge، درخت دعوت | **اضافه شود:** ساخت/ریست رمز (از Synapse admin API)، صفحه‌بندی سمت سرور، نقش‌ها |

## ۶) تنظیمات پلتفرم (چه چیزهایی قابل‌تنظیم است)
Songbird (از پنل، بدون ری‌استارت در بیشتر موارد): ثبت‌نام باز/بسته، آپلود (فعال، سقف فایل، سقف کل پیام، حداکثر تعداد، ترنسکود)، نگه‌داری (فایل روز، متن روز)، طول پیام/نام کاربری/نیک‌نیم، رفتار کلاینت (اندازه صفحه، TTL کش، فواصل refresh، timeout پیام در حال ارسال)، ذخیره‌سازی (S3، presign)، realtime (heartbeat)، پروکسی‌ها، تماس‌ها (کلید اصلی، ویدیو، حداکثر مدت)، دیباگ.
TIKOOTAK الان: ثبت‌نام، سقف کاربر/روزانه، سهمیهٔ دعوت، پیام بسته.
**کمبود مهم ما:** سقف آپلود و نگه‌داری خودکار (دیسک ۸۰ گیگ!)، تنظیم تماس، حد طول‌ها.

## ۷) آنچه نباید از Songbird بگیریم
- رمزنگاری at-rest سمت سرور به‌جای E2EE؛ نصب مستقیم nginx/systemd؛ ری‌استارت/توقف سرویس از داخل پنل (در Docker خطرناک است)؛ ریست/حذف DB از پنل؛ رمز حداقل ۶ کاراکتر؛ `curl | bash` از GitHub (فیلتر).

## ۸) اولویت‌بندی پیشنهادی (خلاصه)
1. **P1** migration نسخه‌دار gateway — پایهٔ ارتقای امن
2. **P2** اعلان Push (Matrix HTTP pusher ← gateway ← Web Push) با پشتیبانی پروکسی
3. **P3** پنل: داشبورد سیستم + تب سرویس‌ها + تب اتاق‌ها
4. **P4** رجیستری تنظیمات + سقف آپلود + نگه‌داری خودکار
5. **P5** پنل: مدیریت کاربر (ساخت، ریست رمز، نقش‌ها) + claim اضطراری + تأیید تایپی + کاتالوگ لاگ
6. **P6** تماس: تنظیمات + تاریخچه
7. **P7** چت: Markdown امن + کد + لینک‌خودکار؛ waveform پیام صوتی
8. **P8** آفلاین: صف ارسال، نوار آفلاین، پنل داده/کش
9. **P9** PWA: نوار نصب + راهنمای iOS/Android + «تازه‌ها» و اعلان نسخه
10. **P10** نشان تأییدشده + نقش‌ها در UI
11. **P11** رمزنگاری at-rest رسانه‌های gateway
12. **P12** اجرای یکجای تست‌ها (`scripts/test-all.sh`) و CHANGELOG خودکار

## ۹) ریسک‌ها / تأییدنشده‌ها
- Web Push در ایران به سرویس‌های Google (FCM) و Apple/Mozilla وابسته است و ممکن است روی بعضی شبکه‌ها نرسد؛ Songbird به همین دلیل `PUSH_PROXY_URL` دارد. تأیید در عمل فقط روی گوشی‌ها و شبکه‌های واقعی ممکن است.
- در اتاق‌های E2EE، اعلان push نمی‌تواند متن پیام را داشته باشد (فقط «پیام جدید»)؛ مگر کلاینت بعد از دریافت، دوباره رمزگشایی کند.
- ستون‌های «TIKOOTAK ✘ (grep)» را قبل از ساخت دوباره بررسی کن (ممکن است نسخه‌ای ناقص وجود داشته باشد).
- مقایسهٔ Songbird فقط از روی سورس است؛ آن را اجرا نکردم.
